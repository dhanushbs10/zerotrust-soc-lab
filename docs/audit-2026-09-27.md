# Audit, 2026-09-27

A full pass over the repository after the Sentinel console was integrated. Every
claim here was measured; where a thing turned out **not** to be a bug that is
recorded too, so it is not re-investigated.

## The one serious finding

### A purple-team run leaked a foothold pod for six hours

`tools/scan-images.ps1` exited 1 reporting that `zerotrust/orders-api` had
changed image from `nginx` to `postgres`. It had not. The Deployment's template
is still `nginx@sha256:65645c7b…` and the real pod is still running it.

The cause was `pod/exfil-20260926-191403`, created by a chain run at 19:14:03 and
never deleted. That run died inside `Invoke-InPod` at hop 6, the terminating
error skipped the cleanup which sat at the end of the script, and the pod
outlived the run by six hours.

It is **completed**, not running — its `sleep 600` finished long ago — and it was
**not** adopted by the `orders-api` Deployment, because a ReplicaSet selector
includes `pod-template-hash` and the foothold has none. Both facts were checked
after a first, wrong guess that it was a live adopted pod.

It still mattered. It is a pod in the business zone carrying `app: orders-api`
and a service account, created by an attack script, that no manifest declares —
and it made a supply-chain scanner report the lab as tampered with. An
attacker-controlled artefact that outlives the run that created it is
indistinguishable from a real compromise, and this lab has spent three phases
teaching that distinction.

Fixed in `2105976` with three layers, because one was demonstrably not enough:

| layer | covers |
|---|---|
| pre-flight sweep of `zerotrust.lab/chain` pods | a crashed run poisoning the next one |
| script-scoped `trap`, declared above hop 1 | any terminating error after the create |
| success-path cleanup | the normal case |

Both paths are verified rather than argued:

- **success** — chain ran 6/6, foothold gone afterwards
- **failure** — a throwaway copy with `throw` injected immediately after the
  create fired the trap, deleted the pod, exited 1, and left 0 exfil pods

One ordering bug was introduced *while* fixing it and caught by re-running: the
first attempt declared `$footholdCreated = $false` below the hops, so line 268's
`$true` was clobbered before the cleanup read it, and the script printed a
six-for-six summary while doing nothing. "The code looks right" and "the cleanup
fired" are different claims.

With the lab clean, `scan-images.ps1` exits 0: `digestChanges` 0, `newAdvisories`
0, down from a false drift finding.

## The control gap

### The console's security suites were enforced nowhere

`dashboard/test_redaction.py` and `dashboard/test_server.py` cover the two
properties that matter most in this repository — a credential cannot leave an
HTTP response, and no endpoint can be made to run a command — in a process whose
documented job is minting cluster-admin tokens.

Neither was in the pre-commit gate. Neither was in CI. And neither *could* be:
both failed on a fresh clone.

`test_server.py`'s redaction mutation fetched 500 exec events and looked for the
password. On a fresh clone there is no telemetry, so there was no secret to
leak, so the mutation reported NOT CAUGHT and the suite exited 1. Three
precondition assertions had the same shape — correctly insisting that a "no
leak" assertion over an empty response is vacuous, but enforcing it
unconditionally.

Measured on a real 83-file extraction of `HEAD` with no `.telemetry`:

| suite | before | after |
|---|---|---|
| `test_sigmalite.py` | exit 0 | exit 0 |
| `test_redaction.py` | exit 0 | exit 0 |
| `test_server.py` | **exit 1** | exit 0, 3 preconditions reported skipped |

Fixed in `edb6e8f`. The mutation now pushes a synthetic payload shaped like a
real exec event through `ok()` and checks the choke point's output, so it proves
the same thing with or without collected data — and it now also asserts the choke
point *did* redact, which the old version never did. The gate runs five suites
and reports the same result on this machine and on a fresh clone.

## A config conflict that made commits fail confusingly

`.gitattributes` declared `*.ps1 text eol=crlf` while the pre-commit
`mixed-line-ending` hook forces LF on every staged file. Every commit touching a
`.ps1` became a fix-then-re-add loop, surfacing as `mixed line ending ... Failed`
on files that were already LF. All 23 `.ps1` files are LF in the tree.

`.gitattributes` now declares LF for everything. That is also the safer choice
on the merits: a CRLF script handed to busybox dies with `syntax error`, which
this project already hit, and several attack scripts build shell fragments in a
here-string and hand them to a container.

## Corrected, and worth recording so it is not re-investigated

Two things that looked like defects in the delivered console and were not.

**The zone-column background is declared light and then overridden dark.**
`styles.css` sets `.zone-column{background:#f5f5ef}` and later
`.zone-column{background:#101820}`, with `--card` moving from `#fbfaf6` to
`#121a23`. The light values are dead. This is layered CSS, not a theme bug.

**The single-column grid only applies at narrow widths.**
`.zone-columns{grid-template-columns:1fr}` appears only inside
`@media(max-width:1100px)` and `@media(max-width:760px)`. At 1440px the three
zone columns sit side by side at left 272 / 639 / 1006 and the graph draws
correctly. The first check ran in a 484px window.

A third was my own misreading, recorded because the reasoning error is
repeatable: all six edge paths appeared to stay within ~30px, which looked like
none crossed the column gap. The zone cards are 337px wide, so adjacent columns
genuinely sit 30px apart and a cross-zone edge *is* short. The geometry was right.

## What no existing gate would have caught

The leaked pod and the unenforced suites both survived 28 commits of hooks,
self-tests, drift scanning and boundary assertions. Not one of them watches for
*pods that should not exist*, and not one of them runs the Python suites at all.

That is the actual finding of this audit, and it is the same shape as every other
one in this project's history: a check that was never written cannot fail, and
its absence reads exactly like a clean result.

Two gaps remain open and are recorded in `progress.md`: nothing enumerates
unexpected pods, and Phase 10's single entry point — which is where such a check
would belong — does not exist.
